# MediLacra Structured Sparsity Experiment

This is a conceptual data-systems experiment, not a simulation of coupled oscillators.

The experiment holds one thing constant: the synthetic healthcare reality generated by MediLacra. The exact same in-memory patient reality is written into two different database layouts and then asked the same semantic questions.

## Question

What changes when the represented reality stays the same, but the relationship structure used to materialize, query, maintain, and understand that reality changes?

## Layout A: canonical

Each core fact has a narrow home:

```text
Patient
   |
Encounter
  /       \
Observation Transaction
```

Tables:

- `patients`
- `encounters`
- `observations`
- `transactions`

Patient ZIP is stored once. Encounter service is stored at encounter grain. Observation and transaction facts remain separate child grains. Queries sometimes need joins to reconstruct a larger semantic answer.

## Layout B: bespoke

The same facts are repeated into consumer-oriented tables:

- `adt_activity`
- `oru_activity`
- `dft_activity`
- `patient_activity_report`
- `provider_activity_report`
- `financial_activity_report`

This makes some reads simpler because one table already contains the desired answer. The tradeoff is that the same semantic fact can be materialized in several places that must remain mutually consistent.

## Grain controls

The runner independently varies:

- patients
- encounters per patient
- observations per encounter
- transactions per encounter

The target grain test is:

```text
1 patient
5 encounters
5 observations per encounter
5 transactions per encounter
```

The existing flat `patient_activity_report` contains both observation-level and transaction-level fields. With one-to-many relationships on both sides of an encounter, a flat table cannot preserve both grains without choosing one grain, nesting one side, splitting the representation, or producing fan-out. This experiment intentionally leaves the bespoke table flat and materializes the encounter-local observation × transaction combinations so that the grain consequence is visible rather than hidden.

For the 1/5/5/5 configuration, expected rows per patient are:

### Canonical

- patients: 1
- encounters: 5
- observations: 25
- transactions: 25
- total: 56

### Bespoke

- adt_activity: 5
- oru_activity: 25
- dft_activity: 25
- patient_activity_report: 125
- provider_activity_report: 25
- financial_activity_report: 25
- total: 230

Those are predictions from the schema topology, not test results. The run determines whether semantic equivalence still holds and records actual materialization counts.

## Machine measurements

Meaning preservation comes first. Each layout gets its own SQL for the same semantic workload, and all four workloads must match before performance is interpreted.

Current workloads:

1. patient encounter history
2. patient observations and diagnoses
3. total charges by patient
4. provider clinical activity

The runner records:

- semantic match
- result rows
- tables touched
- joins and unions
- median local DuckDB runtime
- total and per-table materialized rows
- database file size
- patient ZIP change propagation by tables, rows, and update statements
- generation time
- canonical materialization time
- bespoke materialization time
- workload time
- total machine time

The loader is deliberately still the baseline implementation: row-at-a-time parameterized inserts inside one transaction. Loader optimization is a separate future intervention so it does not silently change the baseline.

## Run identity and timestamped artifacts

Every invocation creates one local-time `run_id` including UTC offset, for example:

```text

```

Every artifact produced by that invocation uses the same run ID. Runs therefore do not overwrite one another.

## Human cognition test

After machine measurements are complete, the runner can conduct a small interactive human relational-cognition test. Human think-time never contaminates machine timing.

The initial cognition task is intentionally basic and should be answerable in a few seconds. It asks which attending provider is associated with a target observation.

The underlying semantic relationship is the same in both layouts:

```text
Observation -> Encounter -> Attending Provider
```

Canonical presentation shows the relationship in two mappings, so the person must traverse the encounter key. Bespoke presentation shows the same relation already materialized in `oru_activity`.

Each layout receives five multiple-choice trials by default. The runner:

- uses different target observations across the session
- randomizes answer positions
- counterbalances which layout appears first by default
- records presentation order
- records selected and correct options
- records correctness
- records reaction time in milliseconds
- records invalid input attempts
- preserves partial results if the cognition session is interrupted

The cognition test requires enough generated state to construct four distinct provider options and ten non-repeated target observations. The planned 1/5/5/5 run satisfies that requirement under normal generation.

Use `--skip-cognition` for unattended or machine-only runs.

## Run

From the repository root:

```bash
python experiments/structured_sparsity/run_experiment.py --patients 1000
```

Target 1/5/5/5 smoke test:

```powershell
python experiments/structured_sparsity/run_experiment.py --patients 1 --encounters-per-patient 5 --observations-per-encounter 5 --transactions-per-encounter 5 --repeats 3
```

Scale patient count without changing grain:

```powershell
python experiments/structured_sparsity/run_experiment.py --patients 1000 --encounters-per-patient 5 --observations-per-encounter 5 --transactions-per-encounter 5 --repeats 5 --skip-cognition
```

Force a particular cognition presentation order for a controlled repeat:

```powershell
python experiments/structured_sparsity/run_experiment.py --patients 1 --encounters-per-patient 5 --observations-per-encounter 5 --transactions-per-encounter 5 --cognition-layout-order bespoke-first
```

Outputs are written to `experiments/structured_sparsity/output/` unless `--output-dir` is supplied.

## Interpretation boundary

This experiment does **not** establish that database schemas behave like oscillator networks. It tests a shared conceptual question:

> How does changing the topology of relationships affect behavior when the represented state is held constant?

The baseline established a tradeoff between read-time relationship traversal and maintenance-time state coupling. The grain phase asks how that tradeoff changes when the underlying reality has multiple child facts at different grains. The cognition phase asks whether the same representational difference also changes the effort required for a human to recover a simple relationship.
