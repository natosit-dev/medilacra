# MediLacra Structured Sparsity Experiment

This is a conceptual data-systems experiment, not a simulation of coupled oscillators.

The experiment holds one thing constant: the synthetic healthcare reality generated by MediLacra. The exact same in-memory patient reality is written into two different database layouts.

## Question

What changes when the represented reality stays the same, but the relationship structure used to materialize and query that reality changes?

## Layout A: canonical

Each core fact has a narrow home:

```text
Patient
   |
Encounter
  /       \
Observation Transaction
```

Tables:

- `patients`
- `encounters`
- `observations`
- `transactions`

Patient ZIP is stored once. Encounter service is stored at encounter grain. Observation and transaction facts remain separate child grains. Queries sometimes need joins to reconstruct a larger semantic answer.

## Layout B: bespoke

The same facts are repeated into consumer-oriented tables:

- `adt_activity`
- `oru_activity`
- `dft_activity`
- `patient_activity_report`
- `provider_activity_report`
- `financial_activity_report`

This makes some reads simpler because one table already contains the desired answer. The tradeoff is that the same semantic fact can be materialized in several places that must remain mutually consistent.

## Grain experiment

The baseline used one patient bundle with one encounter, one observation, and one transaction. The next phase can independently vary:

- encounters per patient
- observations per encounter
- transactions per encounter

The target grain test is:

```text
1 patient
5 encounters
5 observations per encounter
5 transactions per encounter
```

The existing flat `patient_activity_report` contains both observation-level and transaction-level fields. With one-to-many relationships on both sides of an encounter, a flat table cannot preserve both grains without choosing one grain, nesting one side, splitting the representation, or producing fan-out. This experiment intentionally leaves the bespoke table flat and materializes the encounter-local observation × transaction combinations so that the grain consequence is visible rather than hidden.

For the 1/5/5/5 configuration, the expected rows **per patient** are:

### Canonical

- patients: 1
- encounters: 5
- observations: 25
- transactions: 25
- total: 56

### Bespoke

- adt_activity: 5
- oru_activity: 25
- dft_activity: 25
- patient_activity_report: 125
- provider_activity_report: 25
- financial_activity_report: 25
- total: 230

Those are predictions from the schema topology, not test results. The run determines whether semantic equivalence still holds and records actual materialization counts.

## What is measured

### Meaning preservation

Each layout gets its own SQL for the same semantic workload. Results must match before performance is interpreted.

Current workloads:

1. patient encounter history
2. patient observations and diagnoses
3. total charges by patient
4. provider clinical activity

### Query structure

For each workload the experiment records:

- tables touched
- joins
- unions
- median local DuckDB runtime

Runtime is included as an observation, not as the primary conclusion. Small local timing differences are noisy and engine-specific.

### Materialization

The experiment records total rows and per-table row counts. The per-table counts are especially important once grain becomes one-to-many in more than one direction.

### Change propagation

The experiment changes one patient's ZIP in both layouts and counts:

- tables affected
- rows affected
- update statements required

This is the clearest first operational proxy for **state coupling**: how many materialized pieces of system state must respond when one underlying fact changes?

## Run

From the repository root, baseline behavior remains available:

```bash
python experiments/structured_sparsity/run_experiment.py --patients 1000
```

Target 1/5/5/5 grain smoke test:

```bash
python experiments/structured_sparsity/run_experiment.py \
  --patients 25 \
  --encounters-per-patient 5 \
  --observations-per-encounter 5 \
  --transactions-per-encounter 5 \
  --repeats 3
```

PowerShell single-line equivalent:

```powershell
python experiments/structured_sparsity/run_experiment.py --patients 25 --encounters-per-patient 5 --observations-per-encounter 5 --transactions-per-encounter 5 --repeats 3
```

If the smoke test is clean, scale patient count without changing grain:

```powershell
python experiments/structured_sparsity/run_experiment.py --patients 1000 --encounters-per-patient 5 --observations-per-encounter 5 --transactions-per-encounter 5 --repeats 5
```

Outputs are written to `experiments/structured_sparsity/output/`:

## Interpretation boundary

This experiment does **not** establish that database schemas behave like oscillator networks. It tests a shared conceptual question:

> How does changing the topology of relationships affect behavior when the represented state is held constant?

The baseline established a tradeoff between read-time relationship traversal and maintenance-time state coupling. The grain phase asks whether that tradeoff changes when the underlying reality has multiple child facts at different grains.
