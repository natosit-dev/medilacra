# Scope Decision — Optional Synthetic Lab Persistence

**Version:** 0.1
**Date:** 2026-10-08
**Status:** Approved scope correction; refactor implementation not started
**Branch:** refactor/reality-provenance

## User signal

> "the pipeline writes the core entities to DuckDB before it generates the ADT and optional laboratory messages. S"

> "That's OK. If we ever do heavy lab testing we'll build a synthetic lab"

## Decision

**The pipeline's current write order is acceptable.** The refactor must preserve complete, durable **core synthetic reality**, but it does not need to persist every ephemeral result generated by the optional lab demo. Do not treat optional lab-result absence from DuckDB as a critical defect or a prerequisite for the refactor.

A purpose-built synthetic lab (orders, specimen lifecycle, instruments, results, persistence) is deferred until substantial laboratory testing is wanted. Keep existing optional laboratory message generation and regressions intact.

## Boundaries retained

- Persist all core patient, encounter, financial, coverage, payer and institutional records, including currently dropped scalar fields.
- Persist new core requested services, claim/authorization decisions, remittance events, and their source and run lineage.
- Keep X12, direct FHIR, legacy HL7 v2 and legacy v2-to-FHIR semantic-fidelity work in scope.
- Correct unsupported statuses and source-identity assertions in core message serializers.
- Optional lab output can be produced after DuckDB writes; it should be identified as synthetic demo content, not represented as a durable clinical source assertion. Exactly recreating optional lab result draws from DuckDB is not a required acceptance test.
- Do not create a separate laboratory domain or migration solely to satisfy a generalized 'persist absolutely everything' invariant.
